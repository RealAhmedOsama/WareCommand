# WareCommand authentication

Issue #12 adds the first-party ASP.NET Core Identity boundary for Web and
desktop operations. It is an account system, not a production deployment
claim.

## Account model

- Accounts are stored in the PostgreSQL/SQLite `AspNetUsers` and `AspNetRoles`
  tables through `WmsDbContext`.
- Each account has a stable Identity user ID, display name, employee code,
  locale, time zone, active state, lockout state, and last-login timestamp.
- Warehouse administrators create staff accounts. There is no public
  self-registration route.
- Roles and warehouse-scoped permissions are documented in [`AUTHORIZATION.md`](AUTHORIZATION.md).
- Authentication events are recorded in `WmsAuthenticationEvents`. Events do
  not contain passwords, reset tokens, or sensitive claims.

## Web behavior

- Dashboard and warehouse operation controllers require an authenticated
  cookie session.
- Login, logout, lockout, disabled-account rejection, password reset, and
  password change use ASP.NET Core Identity and antiforgery-protected forms.
- The cookie is HttpOnly, SameSite=Lax, time-limited, and sliding. Set
  `Authentication:CookieSecure=true` when the browser-facing connection is
  HTTPS. The local Compose HTTP baseline explicitly sets it to `false`.
- Persistent Data Protection keys are required for stable cookies in a
  container. Configure `DataProtection:KeyDirectory` on protected persistent
  storage; losing that directory invalidates active cookies.
- Cookie validation checks the current active and lockout state, so disabling
  an account rejects an existing session on its next request.

## First administrator provisioning

Bootstrap is disabled by default and no password is committed or generated by
the seed service. For a controlled first run, set all of the following through
the environment or deployment secret manager:

```text
Authentication__Bootstrap__Enabled=true
Authentication__Bootstrap__UserName=<chosen-admin-name>
Authentication__Bootstrap__Email=<chosen-admin-email>
Authentication__Bootstrap__DisplayName=<chosen-display-name>
Authentication__Bootstrap__EmployeeCode=<chosen-employee-code>
WARECOMMAND_ADMIN_BOOTSTRAP_PASSWORD=<secret>
```

`Authentication:Bootstrap:PasswordFile` can point to a mounted secret file
instead of using the environment variable. The host creates the administrator
only when the database has no users. Disable bootstrap immediately after the
first successful provisioning. Re-running with users already present is a
no-op; it never overwrites an existing credential.

## Password reset delivery

`/Account/ForgotPassword` always returns the same generic response. Configure
`Authentication:Smtp:Enabled=true`, `Host`, `Port`, `FromAddress`, and
`EnableSsl=true` before relying on email reset delivery. Store SMTP `Password`
in the secret manager; do not put credentials in logs. `TimeoutSeconds` is
bounded from 1 to 120 seconds. Plaintext SMTP is rejected outside Development;
the only local exception requires `AllowInsecureLocalhost=true` in Development
and a numeric loopback SMTP host such as `127.0.0.1` or `::1`. The notification
email channel shares this same transport and configuration. Reset tokens are
generated by Identity, sent as UTF-8 plain
text, and never written to logs or audit records. The user can also rotate a
known credential from Account settings.

## WinForms strategy

WinForms now displays an explicit sign-in dialog at startup and keeps the
authenticated Identity user in an in-memory `DesktopUserSession`. It does not
fall back to `SYSTEM`; restarting the desktop client requires sign-in again.
The desktop host must point at a database containing accounts provisioned by
the Web/admin workflow (or another approved provisioning operation). Business
forms receive `ICurrentUser` and pass its real user ID to movement use cases.
